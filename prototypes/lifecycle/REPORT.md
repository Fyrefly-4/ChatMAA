# 替身原型实验报告

本轮完成原型 B：Fastify 启动 FastAPI，通过本机 HTTP 控制可控替身，两端分别使用 SQLite。**25 项实验断言通过；真实 MAA、模拟器与游戏均未调用。** 原型 A 和真实合并验证停在用户指令关口。

实验运行于 2026-09-17，最终运行标识 `2026-09-17T15-11-17.705Z`。重放方法见 [README](README.md)，环境与逐项结果见 [summary.json](evidence/summary.json)，四个代表性实验的原始观测、时间线和数据库快照见 [selected.json](evidence/selected.json)。完整本地记录保留在 `.artifacts/`，不提交大量原始日志。

## 结论与工程决策

| 问题 | 本轮证据 | 对设计的影响 |
|---|---|---|
| 响应丢失、重试会不会重复启动？ | 同标识并发提交、响应超时、进程重启后的独立启动观测未增加 | 保留提交前确定身份、持久防重、恢复只核对不自动重发 |
| 第二个应用实例会不会同时操作？ | 相同设备锁、不同数据目录及同一数据目录均拒绝第二实例 | 业务库在 Python 取得设备占用后才打开，避免失败的第二实例改写第一实例 |
| 保存进度与读取位置之间崩溃会怎样？ | 首次成功证据提交前后分别中断 TS；重启重读后计数和事件行数一致 | 保留事件、结果、读取位置同一本地事务 |
| 末尾完成量未知是否永远不能再执行？ | 核对旧替身已不再操作后，保留下界并接受新的明确次数 | 执行状态、计数可信度、设备可用性继续分开；不能猜剩余量 |
| TS 失联后谁停止？ | Python 租约过期后停止；停止阻塞时自行退出 | 自监测只覆盖 Python 控制逻辑仍可运行的情况 |
| 整个 Python 挂起怎么办？ | TS 健康且进入应用退出流程时，可强制终止自有执行端并确认退出 | 普通页面停止不自动升级强杀 |
| TS 已退出且 Python 整体挂起怎么办？ | 超过租约与停止期限后 Python 仍存活，直到实验驱动恢复它 | **当前双进程结构无法自行清理这一组合故障**；是否增加监督机制需另行决策 |

没有增加第三个产品进程，也没有把 Python 改成独立常驻服务。若要求覆盖上述组合故障并保留正常停止窗口，再讨论额外监督机制及 ADR 调整。当前结果支持有限覆盖，不能支撑全面兜底承诺。

## 运行过程中发现并处理的问题

**Windows Python 启动器与实际进程不同。** 直接启动 venv 内的 `python.exe` 时，实测 TS 持有的子进程 PID 与 Python 报告的 PID 不一致。原型改为从虚拟环境解析基础解释器与依赖目录，以基础解释器直接启动，关闭自动 site 导入并显式加载该虚拟环境的依赖，启动时检查 PID 一致。此方式仍需在正式打包时重新验证。

**默认 Node 子进程的实际生命周期比一般 Windows 父子关系更严格。** Node 24.18.0 所用 libuv 的 Windows 实现把非 detached 子进程加入 kill-on-close Job，TS 退出会直接终止它，无法保留先正常停止的窗口。原型选择 `detached: true` 并保留引用、HTTP 控制与显式关闭；没有调用 `unref()`。[固定版本源码](https://github.com/nodejs/node/blob/v24.18.0/deps/uv/src/win/process.c)、[Node detached 文档](https://nodejs.org/api/child_process.html#optionsdetached)

**关闭的日志管道不能破坏监督逻辑。** TS 退出后 Python 的 stdout 可能失效，生命周期日志写入本地并允许 stdout 失败，失联监督继续运行。数据库记录故障另行处理，不用日志代替任务证据。

**系统自动分配的端口不一定可由 Fetch 使用。** 一轮回归中 TS 被分配到 2049，Fetch 拒绝连接；最终改为实际绑定随机较高端口、冲突时重试。没有以该次失败运行作为完成证据。

早期驱动还修正了空 JSON 请求及故障连接复位处理。初次、对照和中间失败运行均留在本地 `.artifacts/`；提交证据来自上述最终运行。

## 验证与保留项

`pnpm install --frozen-lockfile`、TypeScript 类型检查及 `pip check` 通过。Node 使用内建 TypeScript 类型擦除运行代码，类型检查单独执行；存储使用同步 `node:sqlite`，这是原型选择，未评价高负载响应能力。[Node TypeScript 文档](https://nodejs.org/api/typescript.html)、[SQLite API](https://nodejs.org/api/sqlite.html)

150 ms 轮询/续期、1500 ms 租约、900 ms 停止期限和 450 ms HTTP 超时是实验配置。摘要记录了本轮各实验耗时，但这些数据包含启动、注入、等待和清理，不能当作控制接口延迟或生产稳定性指标。
