# MVP 设计集中审阅与最小原型方案

审阅日期：2026-09-17。依据：[MVP Spec #1](https://github.com/Fyrefly-4/ChatMAA/issues/1)、[系统设计草案](../../engineering/architecture.md)、[ADR](../../adr/0001-runtime-structure.md) 及本轮官方资料核对。审阅时 issue 无新增评论，仓库尚无应用实现。本次完成的是文档审阅，未安装依赖、运行模型、连接 MAA 或执行下列实验。

## 审阅结论

现有模块分工和技术组合可以保留，适合作为原型基线。方向讨论可以收敛，但五个关键契约仍需补清并验证；“允许开始原型”与“可以宣称可靠实现 MVP”是两个不同结论。

已经合理的边界包括：模型循环与游戏执行分离；页面关闭不决定任务生命周期；TS 管理业务任务、Python 提供执行证据；本机 HTTP 的受理与执行完成分开；未知结果不自动重做。Electron 和自写 Agent Loop 暂保留替换边界即可，不需要提前实现。

产品负责人已接受 R2–R4 作为既有规则的实现约束，随后授权开始原型，最初要求真实 MAA 调用前等待；现已明确授权官服 `1-7` 三次、不吃药、不碎石，并要求人工操作时及时交接。本文保留设计审阅与实验计划；原型 B 的实现和证据见 [实验报告](../../../prototypes/lifecycle/REPORT.md)。R1 已取得替身故障证据并确认监督缺口，R5 仍待真实执行验证。

## 五项需要落实的设计契约

### R1：明确谁在故障后仍能监督执行端

触发场景：TS 已退出，Python 又整体失去响应。此时两个进程内部的定时器都不能保证实施强制终止。架构 Q5 已允许在退出或失联时尝试强杀，不等于已经承诺覆盖所有组合故障。

| 故障情况 | 当前结构中可能承担监督的部分 | 仍需证明什么 |
|---|---|---|
| TS 正常，Python 停止调用阻塞 | TS | 控制请求超时后能正确定位自有执行端并核对退出 |
| TS 崩溃，Python 控制逻辑正常 | Python 自监测 | 能判定失联、请求停止、保存证据，并完成或升级退出 |
| TS 卡住但未退出，Python 正常 | Python 自监测 | 根据控制权续期而非父进程是否存在判定失联 |
| TS 已退出或卡住，Python 整体无响应 | 现有两个进程不能自行保证 | 明确不保证的范围，或增加仍可运行的外部监督机制 |

Windows Job Object 的 kill-on-close 在最后一个 Job 句柄关闭时终止相关进程，不提供“先等待一段时间供 Python 正常停止”的协议。若 TS 独占最后句柄，其崩溃可能直接触发终止；若 Python 也保留句柄，又不能依靠 TS 退出触发这一条件。因此不能把它直接当作“先优雅停止、超时再强杀”的完整实现。[官方说明](https://learn.microsoft.com/en-us/windows/win32/procthread/job-objects#managing-job-objects)

建议在替身原型中比较实际覆盖范围，不先增加服务。若坚持覆盖两个控制进程均无响应的情形并保留优雅停止窗口，再讨论最小独立监督组件及 ADR-0001/0002 的调整。操作系统或机器故障另有边界，不能作无限故障容忍承诺。

### R2：请求身份、设备占用必须跨进程和重启成立

触发场景：Python 已启动任务，TS 未收到响应便重启；或用户重复打开两个应用实例。只在 TS 内存中放一个“忙碌”标志、每次工具调用新建执行 ID，都不足以保证不重复执行。

建议落实以下契约：

- 同一次已明确的操作有稳定身份，贯穿消息重试、确认、工具调用与 Python 提交；开始网络提交前即已确定。相同身份及相同参数返回原结果；相同身份但参数不同应拒绝。
- Python 对执行标识持久防重；“已受理但不知道是否已经调用 MaaCore”在恢复时保持待核对，不按未执行处理。
- TS 是业务协调者，Python 是最终操作设备的一方；设备占用还需要覆盖意外残留执行端及第二个应用实例。端口占用与一个进程内的锁不是完整证明。
- HTTP 控制请求绑定到本应用启动的执行端实例和当前控制者。新后端读取旧记录不自动获得继续执行权；旧控制者的迟到命令也不能启动新执行。
- 原型用独立于任务表的执行观测计数验证是否实际启动过，避免只检查“数据库只有一行任务”就宣称没有重复启动。

本机 HTTP 的具体令牌、实例身份与设备互斥机制在原型中细化。控制接口保持仅本机可达；访问同一端口不等于拥有执行权。

### R3：分别判定执行状态、结果可信度与设备可用性

现有草案已经区分“结束”和“完成目标”，但还缺少可落实的判定表。一个笼统的“未知”可能导致过早解锁，也可能让已经停止的任务永久阻塞后续请求。

| 已知事实 | 应如何表达 | 是否允许新任务 |
|---|---|---|
| 只发出了停止请求 | 停止中／停止尚未确认 | 否 |
| 有证据确认自动化停止，最终完成量可信 | 自动化已停止，显示最终完成量 | 仍需确认设备环境可执行 |
| 有证据确认执行端不再操作，末尾完成量未知 | 执行已结束，已知完成量及未知部分分别显示 | 环境核对通过后可接受新的明确次数；不能猜剩余量 |
| 只知道 Python 进程退出，尚未排除残留操作 | 执行端已退出，执行与环境待核对 | 否 |
| 确认旧执行结束且设备环境可执行 | 保留原任务结果，解除冲突占用 | 是；新请求仍须通过范围与授权检查 |

这张表是对 #1 中 T15、T19–T22 的实现解释，不引入自动续跑。恢复完成量与恢复设备可用性要分别核对；完成量未知不必然意味着设备永远不可用。

### R4：两个 SQLite 文件之间需要可重复、可核对的证据接收

触发场景：TS 保存了“完成一次”，却没保存已读取事件位置便崩溃，重启重读后计数变为两次；反过来，先保存读取位置、后保存结果又可能漏记。

建议 Python 提供带执行标识和单调序号的关键证据，TS 在一个本地事务中保存收到的证据、更新业务结果和读取位置。重复证据只应用一次；若序号缺失或保留期限已过，应明确缺口，结合快照核对，不能继续把计数当作完整结果。

SQLite 的本地提交不覆盖 HTTP 传输或游戏动作。Python 写了执行意图，不证明游戏已经启动；没有完成记录，也不证明动作未发生。两端记录需要保留来源、时间和范围，不能宣称跨数据库与 MAA 的原子提交。[SQLite 提交说明](https://www.sqlite.org/atomiccommit.html)

持久化失败时建议拒绝新的游戏执行，运行中记录故障的处理另外验证。已授权的普通页面停止仍应尽力传递，不能被记录故障或模型失败阻塞。

### R5：实机决定计数、失败终止与停止的证据语义

现有 MAA 调研提供静态依据，但具体版本中的任务参数、成功反馈、失败重试和停止确认仍未验证。界面显示、数据库字段或替身测试不能补足这部分事实。

原型必须产出“实际参数 → 原始反馈 → 业务解释 → 现场核对”的证据表。至少明确：哪一种反馈能证明一次成功、批量代理怎样计数、失败后是否还会再开一局、停止返回值和停止确认分别是什么、无法确认时如何标记未知。

如果反馈不能支撑规格要求，先记录限制并回到 #1 讨论；不能仅用队列结束或调用返回成功替代业务完成量。

## 最小原型怎样做

建议做两个小原型，再进行一次很短的合并验证。它们验证不同未知项，不需要先搭完整聊天页面，也不依赖模型账号。

### 原型 A：Python → 真实 MaaCore

**问题**：选定环境中的 MAA 能否兑现计数、资源限制、失败终止和停止语义？

**只做这些**：一个命令行入口、最小 Python Adapter、原始反馈记录与简短结果报告。固定为一个设备和 1-7；初次建议采用少量次数，由实际验证安排确定，不能把少量次数原型当作“十次”正式验收已经通过。

1. 记录系统、设备/模拟器、区服、MaaCore、资源与绑定版本，以及代理前提是否满足。
2. 先核对并输出受限参数，保证不吃药、不碎石，再进行约定的少量真实执行。
3. 保存带时间的原始反馈，对照现场成功战斗数，解释每个计数依据。
4. 在不同阶段请求正常停止，观察控制入口是否仍响应，区分停止请求返回、自动化停止与游戏内战斗状态。
5. 记录能自然重现的理智不足或失败；无法在实机重现的场景明确标为未验证，后续使用源码依据与替身覆盖应用侧处理，不能冒充实机通过。

**完成标准**：得到可复现的最小命令与环境记录，能证明目标场景的参数限制、计数映射和停止边界；失败路径已验证或明确列出无法验证之处。若关键语义不满足规格，原型结论就是未通过及差异，不继续堆功能。

### 原型 B：TS → 本机 HTTP → 可控替身执行器

**问题**：真实的进程管理、HTTP 和两端 SQLite 能否在故障中保持不重复执行、诚实状态和可核对记录？

**只做这些**：Fastify 主进程、由它启动的 FastAPI 子进程、两个 SQLite 文件、一个替身执行器及自动化实验驱动。替身不连接游戏，能按指令成功、延迟、拒绝停止或产生缺失反馈；实验驱动是测试工具，不是已经引入产品的第三个监督服务。

先实现受理、查询、停止、就绪/控制权续期这几项能力，参数可以固定。以下测试通过公开控制入口和真实进程/存储进行，不用把 HTTP、数据库和生命周期都替换掉：

| 实验 | 通过时必须看到什么 |
|---|---|
| 正常提交、轮询、停止 | 执行期间控制入口响应；原任务逐步更新；停止先请求后确认 |
| 重复同一提交或并发提交 | 同一操作没有第二次实际启动；独立第二任务被拒绝且不排队；同标识不同参数被拒绝 |
| 提交后故意丢弃 HTTP 响应 | 按原标识核对，实际启动次数不增加 |
| 在写入前后及执行前后中断进程 | 恢复时区分已知与未知，不因“查不到完成记录”重发 |
| 重复读取事件，或在保存事件位置附近崩溃 | 完成量不重复累计，也不跳过未保存证据；缺口可见 |
| 启动第二个 TS/Python 实例 | 不能同时取得同一设备的执行权，旧实例的迟到命令不能重新取得控制 |
| TS 崩溃或失去响应 | Python 按已验证机制识别失联，停止并记录；不会因没有游戏进度就误判失联 |
| 停止调用阻塞与 Python 整体无响应 | 分开测试两种故障；逐项证明谁检测、谁计时、谁终止，做不到的格子明确未覆盖 |
| 强制终止后重启 | 根据证据表达结果与未知部分，先核对旧执行和环境再解锁 |

“暂停一个回调”和“整个进程无法执行任何代码”是不同的故障。仅让替身忽略停止请求，不足以验证 Python 自监测或独立监督的可靠性。FastAPI 的并发规则也不会自动让任意阻塞调用保持控制响应。[FastAPI 官方说明](https://fastapi.tiangolo.com/async/)

**完成标准**：每个故障注入点都有可重放脚本、时间线、独立执行观测、数据库前后对照及通过/失败结论。等待期限和轮询间隔作为实验配置记录，先测量再确定；不填写未经测量的响应速度或稳定性数字。

### 合并验证：替换执行器，保留同一 HTTP 契约

两个原型的关键问题解决后，将原型 B 的替身替换为原型 A 的 MaaCore Adapter。先验证一轮约定的真实执行、正常停止及读取结果；受控进程强杀等故障先在替身中通过，真实环境验证另行安排。真实集成会暴露线程、阻塞、原生调用和资源路径差异，不能仅因 A、B 分别通过便宣布整个链路通过。

模型接入与 React 页面放在这之后做最小贯通，再覆盖 #1 的完整 T01–T26。替身原型与小次数实机实验都不是 MVP 完成证明。

## 顺序、交付物与参与方式

建议先启动原型 B 的最小正常链路，同时准备原型 A 的环境；B 不需要 MAA 就能开始。取得 A 的原始事件证据后，再收敛 B 的事件字段与状态映射，避免先按想象冻结接口。进程兜底先在替身中做，不将真实游戏当作故障注入工具。

每个原型只交付四类内容：可重放入口、环境与版本清单、带原始证据的结果表、需要保留或修改的设计结论。界面美化、通用插件、多设备和完整历史页面不属于这两个原型。

产品负责人无需逐段读代码；每次回看一张执行时间线和一张通过/失败表，讨论证据是否足以支撑产品承诺即可。真实验证所需的 MAA 位置、设备/区服、可用代理关卡及首轮次数已收集：Windows 官方桌面端、官服、`1-7` 三次，MaaCore API 版本 `v6.17.5`。用户已完成登录与管理员侧连接预检；不吃药、不碎石，不自动补刷或扩展额外实机实验。

本轮已接受 R2–R4 作为既有规则的实现约束；如果验证迫使增加监督组件或调整产品承诺，再集中讨论变化。原型 B 在 [issue #3](https://github.com/Fyrefly-4/ChatMAA/issues/3) 跟踪，实现位于 `prototypes/lifecycle/`。原型 A 在 [issue #4](https://github.com/Fyrefly-4/ChatMAA/issues/4) 跟踪，窗口绑定与截图已通过，首轮执行入口见 [真实验证入口](../../../prototypes/maa/README.md)。合并验证仍待真实反馈核对，不能以替身通过替代实机验证。

早期两轮实机调用均在关卡导航阶段失败，错误记录与停止收尾已取得证据，当时尚未验证战斗计数。用户决定先配置并验证官方 MAA GUI 的本机基线，实验因此暂停。完整经过见 [实机实验报告](../../../prototypes/maa/REPORT.md)。

截至 2026-09-18，后续排查已修复原型自身的 DPI 初始化与可选次数字段解释；累计完成三次目标，其中后两次连续执行，用户现场确认一致，正常停止收尾已验证。前三次导航失败、一次解析器提前停止及修复证据均保留。原型 A 基本链路已走通，战斗中停止、异常场景和 HTTP 合并验证仍待完成；此前暂停状态已由用户后续指令解除。

随后已准备 HTTP 合并代码和脱敏回调离线验证：保留原 TS 接口与双库事务，由 Python 工作线程调用原有 CLI 执行逻辑；真实环境不复用替身的自动解锁判断。模块图、离线证据和下一轮待确认操作见 [HTTP 合并验证](../../../prototypes/maa/HTTP-MERGE.md)。此阶段没有追加 MaaCore 或游戏调用。

## 原型交付核对（2026-09-18 收尾）

用户在暂停审阅后明确恢复准备并手动启动本轮实机入口。HTTP 合并结果为首局成功、第二局启动后停止，用户确认「符合，已确认能手动接管」。依据原型 A、B 与合并验证的原始范围，交付核对如下；这是实验结果与限制的清单，不修改 #1 的产品规格。

| 约定内容 | 已核对的证据与边界 |
|---|---|
| A：本机环境、版本、接入与受限参数 | `prototypes/maa/ENVIRONMENT.md`、各轮 manifest、MaaCore v6.17.5 哈希；DPI、资源层、窗口绑定和识别门槛均有记录 |
| A：约定次数与真实成功解释 | 初始三次为一次＋关联任务连续两次，现场确认；回调计数与去重见 `verified-first-battle.json`、`remaining-two.json` 和 9 项单元检查 |
| A：停止请求与停止事实分开 | 导航失败、首局结算后停止及本轮第二局启动阶段停止均留证；本轮包含 `AsstStop` 返回、`AsstRunning=false`、销毁、进程退出和用户接管确认 |
| A：失败与资源限制的适用范围 | 无自然复现的战斗失败或理智不足，明确列为未验证；只核对参数与已观察到的操作，不将加载私有失败规则当作实战证明 |
| B：身份、并发、响应丢失、崩溃、事件与设备占用 | 原始实验入口、锁文件、环境、独立观测、双库快照和 25 项最终回归结果齐备；原始产物本地保留，脱敏摘要入库 |
| B：停止阻塞、失联与整个进程挂起 | 已分别实验；两进程同时不能运行时的监督缺口保留，未增加第三个产品服务或全面兜底承诺 |
| 合并：线程、HTTP 与双库证据传递 | 11 项离线检查及真实 `http-merge-first`；两端各 8 条证据、TS 读取位置 8、无事件缺口、一次工作线程入口 |
| 合并：普通停止及退出交接 | 本轮真实停止与最终结果交接成功、进程退出、用户确认；运行中直接关闭应用的交接由离线检查覆盖，不能扩展为实机故障验证 |
| 交付与用户参与 | 入口、版本与环境、时间线、结果表、设计结论和脱敏证据均已提交；实机调用均在交接后进行，本轮没有补刷或追加次数 |

最小原型阶段达到上述交付标准。它支持保留当前技术组合作为后续实现基线；真实环境如何核对后解锁、已知监督边界如何向用户说明，仍应在正式模块实现时落实。React、模型接入与 #1 的 T01–T26 全量验收属于后续阶段，不包含在这次原型完成结论中。

另外保留一轮替身回归中的两次读库 I/O 异常：最终重新完整回归为 25/25，但异常根因未确定，不因重跑通过而删除失败记录。详见 [HTTP 合并报告](../../../prototypes/maa/HTTP-MERGE.md)。
