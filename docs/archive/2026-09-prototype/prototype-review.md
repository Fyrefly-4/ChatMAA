# MVP 设计审阅与原型结论

收尾日期：2026-09-18。**当前技术组合与模块分工可以保留，最小原型达到约定交付标准，可以进入 MVP 实施拆分。** 已验证的是受限执行链路及指定故障场景；完整聊天应用与 [MVP Spec #1](https://github.com/Fyrefly-4/ChatMAA/issues/1) 的 T01–T26 尚未完成验收。

本文说明原先疑问解决到什么程度，以及剩余决策。当前设计见[架构说明](../../engineering/architecture.md)；原始意见、计划和推进经过见[审阅历史](design-review-history.md)。

## 1. 本次验证了什么

先分别验证真实 MAA 行为和应用故障处理，再合并两条链路。

| 验证部分 | 范围 | 结论与证据 |
|---|---|---|
| A：Python → MaaCore | Windows 官方桌面端、官服、MaaCore v6.17.5、1-7；不吃药、不碎石 | 初始目标累计成功三次：一次＋关联任务连续两次，现场确认一致。[实机报告](../../../prototypes/maa/REPORT.md) |
| B：TS → HTTP → Python 替身 | 真实进程、HTTP、双 SQLite；替身故障注入不调用游戏 | 最终 25 项断言通过，覆盖防重、崩溃、记录失败、失联与监督缺口。[替身报告](../../../prototypes/lifecycle/REPORT.md) |

## 2. 五个设计问题的最终答复

### R1：故障后谁还能监督执行端

**结论：有限覆盖已验证，也复现了无法自救的组合故障。**

健康的 Python 能在 TS 崩溃或失去响应后识别失联、请求停止并在超时后自行退出；健康的 TS 能在应用退出流程中终止整体挂起的自有 Python。若 TS 已退出或卡住，Python 也整体挂起，两者无法自行完成清理。

依据是原型 B 的真实进程实验。当前没有第三个监督服务；实验驱动的故障注入和清理不算产品能力。若要求覆盖组合故障并保留正常停止窗口，须重新讨论 [ADR-0001](../../adr/0001-runtime-structure.md) 与 [ADR-0002](../../adr/0002-local-http-adapter.md)。

### R2：重试或重启会不会重复执行

**结论：原型支持保留稳定操作标识、执行端持久防重、设备互斥与控制者身份检查。**

同一操作在提交前确定标识，响应丢失后按原标识查询。同标识但参数不同被拒绝，独立第二任务不排队，第二实例不能同时取得设备执行权。重启只核对旧执行，不自动重新启动。

依据是原型 B 的并发、响应丢失、重启、第二实例实验，以及合并离线检查的独立工作线程入口记录。完整聊天与确认流程仍需贯穿同一操作身份，不能宣称尚未实现的入口已通过验收。

### R3：停止、完成量和设备可用性如何区分

**结论：三者必须分开，实机停止支持这一设计；通用环境解锁仍待实现。**

| 已知事实 | 应显示什么 | 能否开始新任务 |
|---|---|---|
| 只发出停止请求 | 停止中，尚未确认 | 否 |
| 自动化停止，完成量证据完整 | 已停止及最终完成量 | 仍需确认环境可执行 |
| 自动化停止，末尾结算缺失 | 已确认完成量及未知部分 | 环境核对后可接受新的明确次数，不能猜剩余量 |
| 仅知道 Python 退出 | 执行端退出，执行与环境待核对 | 否 |
| 旧执行结束且环境核对通过 | 保留旧结果，解除冲突占用 | 是，仍须检查范围与授权 |

合并实机结果是“成功一次＋另一局未结算＋自动化停止＋环境待核对”。替身演练了核对后的新任务，真实原型结束后仍保留待核对。继续执行应创建关联的新任务。

### R4：两份数据库会不会漏记或重复计数

**结论：证据接收与退出前交接已验证，仍须保留动作发生但未留证的未知窗口。**

Python 提供带序号的证据，TS 在同一本地事务中保存证据、更新结果与读取位置。重读不重复计数，缺口与存储故障保持可见。原型 B 与合并离线实验覆盖相关崩溃和记录失败。

审阅发现过退出缺口：Python 保存最终结果时，TS 已停止查询。现已修复为有期限的交接阶段，让 TS 保存最后证据并确认后 Python 再退出；交接失败不能显示成功。真实合并两端各保存 8 条证据，TS 读取位置为 8，无缺口，两库完整性检查通过。

这些结论不提供游戏与双库的统一事务保证。记录缺失仍不能证明动作未发生，见 [ADR-0003](../../adr/0003-execution-evidence.md)。

### R5：MAA 反馈能否证明成功与停止

**结论：指定环境的成功计数与已测试阶段的停止已有实机证据，战斗失败和理智不足仍未实测。**

早期导航失败后修复了原型自身的 Windows DPI 初始化；首局结算后又修复了把可选计数字段缺失误判为未知的问题。修复后的计数结合单局开战、结算过程与 1-7 三星掉落反馈，按周期去重，并与现场核对；队列结束或调用返回成功本身不作为成功量证据。

停止记录区分请求返回、MaaCore 不再运行、销毁与进程退出。已有导航失败收尾、首局结算后停止和第二局启动阶段停止的证据，不能推广到所有阶段。战斗失败、理智不足未自然复现；参数限制和私有失败规则加载检查不替代实战验证。

## 5. 剩余事项及下一阶段影响

| 事项 | 当前边界 | 下一步 |
|---|---|---|
| 真实环境核对与解锁 | 原型结束后保持待核对 | 恢复模块实施前，与产品负责人确定检查依据与交互 |
| 双进程同时无响应 | 已复现不能自行清理 | 明确提示和人工处理；若要求自动兜底，重新讨论架构 |
| 战斗失败、理智不足、其他停止时机 | 未实机验证 | 保留限制，需要时另行安排受控实测 |
| 实机运行中关闭、挂起、强制终止 | 应用侧已有离线覆盖 | 不宣称已有实机证据，等待参数不作为生产可靠性保证 |
| SQLite 偶发读取异常 | 一轮出现两次 disk I/O error，原因未明；后续完整回归 25/25 | 保留失败记录；快照错误跳过清理的问题已修复，I/O 根因未解决 |
| 页面、模型与完整验收 | 尚未实现或完成验证 | 按端到端场景拆分实施任务，关联 #1 的 T01–T26 |

本次没有出现必须推翻已有选型的新证据。后续应将原型契约整理为正式模块，由产品负责人参与剩余行为与边界的决定；原型代码不宜不加整理地直接扩建为完整应用。
