# 文档维护规则

适用范围：创建、更新、迁移项目文档，或工程变更影响已有说明时。人类可读内容以简体中文撰写，保留代码、协议与官方名称。

## 信息归属

| 信息 | 主维护位置 |
|---|---|
| 项目定位与愿景 | [项目定义](../overview/project-definition.md) |
| 正式产品行为与验收 | GitHub Spec，当前为 [#1](https://github.com/Fyrefly-4/ChatMAA/issues/1)；访问遵循 [Issue 约定](issue-tracker.md) |
| 共享术语 | [CONTEXT](../../CONTEXT.md) |
| 当前模块、关系、代码落点与实现状态 | [工程说明](../engineering/architecture.md) |
| 持久架构决定 | `docs/adr/`；沿用 [domain 约定](domain.md) |
| 实验事实、环境、验证边界 | 对应原型的报告及证据 |
| 已结束的讨论与阶段判断 | [归档](../archive/README.md) |

其他文档作必要摘要并链接主来源。代码目录变化时更新工程说明；职责、进程或数据归属变化时先核对相关 ADR。规格冲突须列出双方来源、适用范围与影响，交回决定，不能仅按日期新旧覆盖。

## 状态与追溯

- 当前说明写明最近核对日期与代码基线，分别表达目标职责、已实现能力、验证程度和未决事项；文档编辑不代表重新验证。
- ADR 保留稳定编号和决定状态，注明确认来源与可核实的日期；无法核实的日期明确留空或说明。被替代时指向后继决定，保留原取舍。
- 实验报告记录时间、环境、运行版本与证据范围；离线、替身和实机结论分别表达。
- 归档记录来源、记录时期、归档日期、原因和当前替代入口。正文冻结，后续澄清以有日期的补充说明记录。
- 愿景与初始设想标明定位和时期，不承担当前规格或实施计划职责。

“已接受”“已实现”“已验证”是不同状态。无需给每份 Markdown 添加独立版本号；Git 追踪编辑历史，以上元信息说明内容适用性。

## 更新与迁移流程

1. 检查工作区已有修改和本次授权范围，以当前内容为基础；先保全将被迁移或重写的材料。
2. 确定每项信息的主维护位置。重复内容改为摘要与引用，独有依据先保留可追溯去向。
3. 更新内容和链接；历史时态补时间说明，原始证据保持不变。迁移后在归档索引登记旧路径，已发布记录按其历史版本解读。
4. 检查修改范围内的文件与锚点链接、信息保留及当前状态一致性。公共入口不依赖忽略目录；本地资料不得未经授权复制到受版本管理的文档或远端。
5. 交接入口、实际变更、未解决差异和维护位置。执行范围仍由当次委托确定，文档中的历史推进建议不构成新授权。
