# TS 启动 Python 子进程，通过本机 HTTP 调用 MAA Adapter

定位：持久架构决定；状态沿用 `accepted`，不代表已完整实现。元信息核对：2026-09-18。确认依据：[架构讨论 Q1–Q12](../archive/2026-09-prototype/architecture-discussion.md)；独立确认日期尚未逐项核实，不以本次整理日期代填。正文中的待验证状态按原讨论时间理解，后续验证见有日期的补充及[当前工程说明](../engineering/architecture.md)。

在单机、统一启停的运行结构下，产品负责人选择 Q6=B：由 TS 后端直接启动 Python 子进程，Python 提供本机 HTTP 接口。该选择提供可独立检查和调试的 HTTP 接口边界，同时保留由 TS 负责启动的组织方式；没有选择 stdin/stdout 业务消息协议，也没有增加独立启动器。

代价是需要管理本机监听地址、端口、就绪检查、调用方识别以及进度反馈方式。HTTP 连接不是执行任务的生命周期，断线或响应超时不能直接当作任务停止、失败或未启动；既有防重复执行和异常核对要求继续适用。

Q7=A 进一步确定：提交接口返回受理信息与可查询标识，执行独立推进，查询与停止使用单独入口；TS 定期查询状态与新增关键事件，不为首版引入 SSE 反馈通道，也不自动排队。代价是状态展示可能滞后一个查询周期；当前接受该取舍，具体周期通过原型确定。

Q9=A 已选择 TS 侧 Fastify、Python 侧 FastAPI，具体版本与集成尚未验证。接口字段、事件缺口处理与失联监督机制随后设计；执行端证据归属见 [ADR-0003](0003-execution-evidence.md)。若为落实 [ADR-0001](0001-runtime-structure.md) 的强制终止兜底而需要额外运行组件，应明确说明原因并重新讨论。

原型验证补充（2026-09-18）：现已用固定依赖完成替身故障矩阵和一轮真实 HTTP 合并验证。执行期间查询、普通停止、计数回传及停止后的退出交接已走通；这是选型与契约的实验依据，不是正式产品的全部可靠性结论，见 [合并报告](../../prototypes/maa/HTTP-MERGE.md)。

2026-09-20 规格迁移补充：当前产品行为与验收依据为 [MVP Spec #18](https://github.com/Fyrefly-4/ChatMAA/issues/18)，工程路线见 [#19](https://github.com/Fyrefly-4/ChatMAA/issues/19)。旧 #1 已被替代，正文中的旧规格引用保留历史语境；本 ADR 的职责、运行与记录边界继续适用。本次仅更新规格入口，没有新增实现或验证证据。
