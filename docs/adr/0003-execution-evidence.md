# Python 保留最小执行证据，TS 管理业务任务与会话

定位：持久架构决定；状态沿用 `accepted`，不代表已完整实现。元信息核对：2026-09-18。确认依据：[架构讨论 Q1–Q12](../archive/2026-09-prototype/architecture-discussion.md)；独立确认日期尚未逐项核实，不以本次整理日期代填。正文中的待验证状态按原讨论时间理解，后续验证见有日期的补充及[当前工程说明](../engineering/architecture.md)。

后端可能在接收执行反馈前退出，Python 又需要在失联时停止，并可能被强制终止。产品负责人选择 Q8=A：Python 持久保存受理标识、对应参数、关键执行反馈与停止证据，供 TS 恢复后关联核对；TS 继续负责会话、授权、业务任务及用户可见历史。

相较于只由 TS 持久化，该方案有机会保留执行端已记录但尚未传达的事实，代价是增加执行端记录与恢复核对工作。Python 不复制完整业务状态，不依据旧记录自动恢复游戏执行；游戏动作与记录写入之间仍有故障窗口，未知部分必须明确保留。

Q10=A 进一步选择两个独立 SQLite 文件：TS 写业务库，Python 写最小执行记录，通过 HTTP 核对；避免两端直接共写业务表，并接受后续更换数据库需要迁移和重新验证事务语义的代价。记录保留与清理策略尚未确定，集成尚未验证。恢复时需要明确记录身份、范围与缺口，不能因找不到完成记录就判定未执行。业务规则仍以 [MVP Spec #1](https://github.com/Fyrefly-4/ChatMAA/issues/1) 为准。

原型验证补充（2026-09-18）：真实合并测试两端各保存 8 条证据，TS 读取位置一致且无事件缺口；结果为已确认一次、另一周期未结算、自动化停止、环境待核对。重放、崩溃和记录失败已有离线证据，仍不提供跨两库与游戏动作的原子性保证，见 [合并报告](../../prototypes/maa/HTTP-MERGE.md)。
